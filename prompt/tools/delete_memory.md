# delete_memory —— 删除或更新某条长期记忆

删除一条已保存的记忆（含 pinned 永久记忆）。用于：记忆错误/过时、重复或废弃、用户要求忘记。

## 用法
- `id`（必填）：要删除的记忆条目 id（`search_memories` 返回的 `id` 字段）

## 规则
- 能删的：非管理员只能删**自己来源**的记忆（私聊是自己的、群聊是当前群的）；管理员可删任意
- 删除**不可恢复**（仅归档到 evicted 表）——确认不再需要再删
- 用户要求"忘掉/删除关于 X 的记忆"时：先 `search_memories` 找到 id，再调用本工具删除

## 主动维护：发现过时记忆就自己清，不必询问

**用户的明确要求**：过时、重复、已被修复或被新事实推翻的记忆，**直接清理或更新，不要先问**。

判断信号（见到就动手，别攒着）：
- 内容里写着「待办 / 尚未 / 未提交 / 待用户拍板 / 建议…」但该事项**已经完成**
  → 先核实（看代码/日志/文件/git log），确认完成就删
- 记录的是**一次性的过程细节**：「重启成功 PID xxx」「已排定 N 秒后重启」「提交号 abc123」
  「测试从 22 项到 34 项」「已向某仓库同步 N 个文件」→ 这类没有长期价值，删
- 被**后续事件否定的旧状态**：如「尚未提交」后又记了「已提交得分 100」→ 删旧的
- 两条**说的是同一件事**（同环境事实、同一次评测结果）→ 留信息更全/更新的那条
- 断言某个**技术问题存在**，但该问题**已被修复**（代码里已有对应改动 + 测试）
  → 删；若修复方式本身值得记，改写成「已修复 + 修复要点」，不要留「它坏了」的旧叙述

**先核实、再删**：能从代码/日志/git 里确认的就去确认，别凭印象断定"应该已经做了"。
否则会把仍然有效的信息误删。

**不确定时就留着**：真的无法判断是否过时，就不动它 —— 少删一条的代价，
远小于删掉一条还在用的约定。

批量清理时把删了什么、为什么删简短汇报给用户即可（不必逐条请示）。
